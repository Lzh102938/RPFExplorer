# 0DRP 资源格式（GTA VI / RPF9）

> 状态：结构已定版，可字节级写回
> 验证范围：`data.rpf` 内 15,768 个 0DRP（15,755 个 `0drp` + 13 个 GXT 变体）
> 工具：RPFExplorer（`src/DrpFile.*`、`src/EmbeddedScan.*`）
> 置信度标记：**[证实]** 有全量数据验证；**[强证据]** 高比例吻合；**[未解]** 语义未定

---

## 1. 摘要

0DRP 是 GTA VI 的通用资源容器。一个 0DRP 由三部分组成：

```
┌──────────────────────────────┐ 0x00
│ 头部（0x60 字节）             │
├──────────────────────────────┤ 0x60
│ 子资源数据区（任意内容）       │
│                              │
├──────────────────────────────┤ +0x38 指针处
│ 子资源表（16 字节/项）         │
└──────────────────────────────┘ +0x40 指针处（表区上界）
```

- 字节序：**小端**（u16/u32/u64 均按 LE 读取）
- 运行期指针：`0x50000000 | 文件内偏移`。读取时减去 `0x50000000` 即得偏移
- 子资源表放在数据区之后；表首/表尾由头部 `+0x38` / `+0x40` 给出
- 表项给出每个子资源的 `{段 ID, 大小, 偏移}`，子资源内容原样存放（不压缩）

GXT 文本表是 0DRP 的一个特殊变体（见 §7），结构校验通过后按文本表解析；否则按通用 0DRP 处理。

| `+0x3C` | u32 | 0 | [证实] | 均为 0 |

## 3. 子资源表

### 3.1 表项布局（16 字节）

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x00` | u64 | `size << 32 \| 段ID`：高 32 位 = 子资源字节数，低 32 位 = 段类型 ID |
| `+0x08` | u64 | `0x50000000 \| offset`：子资源在文件内的偏移 |

小端读取后的等价写法：

```c
uint64_t v = read_u64_le(p + i*16);
uint32_t size     = (uint32_t)(v >> 32);
uint32_t section  = (uint32_t)(v & 0xFFFFFFFF);
uint64_t p64      = read_u64_le(p + i*16 + 8);
uint32_t offset   = (uint32_t)(p64 - 0x50000000);
```

### 3.2 表项数量与终止

表项是**连续**的，从 `+0x38` 指针处开始；遇到以下任一情况即终止：

1. 指针字段 `< 0x50000000`（不是运行期指针）
2. `size == 0`
3. `offset >= 文件大小` 或 `offset + size > 文件大小`

实测条目数分布（15,767 个可解析样本）：

| 项数 | 文件数 |
|---|---|
| 4 | 14,408 |
| 2 | 1,250 |
| 6 | 53 |
| 3 | 35 |
| 8 | 10 |
| 5 | 10 |
| 9 | 1 |

> 注意：`+0x40` 只是表区上界，表区尾部可能有其他结构；
> `(表尾 − 表首) / 16` 不等于表项数，必须逐项走。

### 3.3 段 ID（不是哈希）

低 32 位是**段类型 ID**，不是文件名哈希。全量 60,585 个子资源只出现 11 个不同值：

| 段 ID | 工具内名称 | 出现次数 | 说明 |
|---|---|---|---|
| `0x00000010` | 字符串池 | 14,493 | null 分隔 UTF-8；对白 / UI / 新闻文本 |
| `0x00000101` | 数据块 | 14,456 | 按 544 B 分块（544 = 34 × 16 B） |
| `0x99331089` | 索引头 | 14,456 | 16 B：`{版本, N, 3, 0}` |
| `0xa8478889` | 记录表 | 14,456 | N × 16 B，每条对应一个字符串 |
| `0xc90d1c34` | 头 | 1,246 | 固定 40 B |
| `0xfc3dbc38` | 数据块 | 1,246 | 变长 |
| `0x956a9df5` / `0x10075946` | 辅助表 / 数据 | 62 | 六段容器 |
| `0xd7e9c53b` / `0x8731ec16` / `0xac393bcc` | 数值块 / 记录 / 主数据 | 37 | 小容器 |

按段 ID 组合把容器分为 5 类：

| 组合 | 容器数 | 解压体积 | 判定 |
|---|---|---|---|
| `10 + 101 + 99331089 + a8478889` | 14,394 | 315.5 MB | 对白 / UI 文本包（4 段） |
| `c90d1c34 + fc3dbc38` | 1,246 | 7.7 MB | 资源包（2 段） |
| 4 段 + `956a9df5 + 10075946` | 62 | 47.4 MB | 扩展文本包（6 段，含 1 MB 大块） |
| `8731ec16 + ac393bcc + d7e9c53b` | 34 | 0.3 MB | 小资源包（3 段） |
| `8731ec16 + d7e9c53b` | 3 | <0.1 MB | 小资源包（2 段） |

> 语言分布：4 段容器按文字系统统计为 latin 8,854 / 中文 2,081 / 俄 1,098 /
> 韩 1,083 / 日 1,037 / 其他 241，几乎精确符合 **13 种语言 × 1,107 份**。
> 字符串池包含任务对白（带 `~sl:0.0:1.7~` 时间轴）、UI 文本和游戏内媒体新闻稿。

### 3.4 4 段文本包的字段关系（已解明）

索引头 `0x99331089` 是 4 个 u32：`{版本/标志, N, 3, 0}`（上例为 `{0x100, 1895, 3, 0}`）。
全量 14,418 个 4 段容器验证：

- `N` = `0x10` 段里 null 终止符的个数（包括空串）
- `N` = `0xa8478889` 字节数 ÷ 16（**14,418 / 14,418 全部成立**）
- `0x101` 字节数始终可被 16 和 544 整除；544 = 34 × 16
- 例：seq 1428 → `N=1895`，字符串池 1,895 个 null，
  记录表 30,320 B（1,895 × 16），数据块 69,632 B（128 × 544 = 4,352 × 16）

因此 4 段包可以完整拆成：
`N 个字符串` + `N 条 16 B 记录` + `K 个 544 B 数据块`。
记录表/数据块内部字段的含义仍未完全解明（见 §8），但边界与条数已确定。

## 4. 子资源数据

- 位置：`offset`，长度：`size`，内容不做压缩/加密（在 RPF 的解压流内）
- 段 ID 决定内容：
  - `0x10`：N 个 null 分隔 UTF-8 字符串（对白 / UI / 新闻）
  - `0x99331089`：16 B 索引头 `{版本/标志, N, 3, 0}`
  - `0xa8478889`：N × 16 B 记录表，每条对应一个字符串
  - `0x101`：K × 544 B 数据块（544 = 34 × 16 B 槽）
  - 其余段：头 / 数据块，语义未定
- 工具按段切片后再做字符串/结构识别，不再对整文件做字符串扫描

## 5. 写回（序列化）

`DrpFile::serialize()` 的步骤：

1. 复制原始字节，保留所有**未建模区域**
2. 用解析出的 `tableOffset/tableEnd` 重写头部 `+0x38` / `+0x40`
3. 用解析出的项重写每个表项：
   - `u64 (size << 32 | 段ID)`
   - `u64 (0x50000000 | offset)`
4. 按每项的 `offset/size` 把子资源数据从原始字节重新落位

判定：`serialize() == 原始字节` 即写回一致。

### 验证结果（data.rpf）

```
0DRP 总数: 15755
解析成功: 15754
写回一致: 15754
失败: 1
```

- 通过率：**15,754 / 15,755（99.99%）**
- 唯一失败：`seq 25904`（14,876,672 字节，特殊变体；表头指针不满足通用布局）
- 13 个 GXT 变体不计入（按 GXT 解析器处理）

复现命令：

```powershell
RPFExplorer.exe --drp 1389 -o out.txt "data.rpf"        # 单文件结构 + 写回
RPFExplorer.exe --drp-verify -o verify.txt "data.rpf"   # 全量校验
```

## 7. GXT 变体

GXT 文本表同样是 0DRP，但内部结构不同：

- 头部 `+0x14` 仍为 `0x7A`，`+0x10` 仍为 `0DRP`
- 槽位表、记录表、串池的布局由 `GxtParser` 校验：
  - 槽位表：`+0x60` 起 69,632 字节（4,352 槽 × 16B）
  - 记录表锚点：200 条记录模式
  - 串池基址：`class4/5/6` 三组，投票选出
- 判定条件：记录表锚点存在 + 有效槽位 > 100 + 文本解码率 ≥ 50%
- data.rpf 中共 **13 个** GXT（语言包各一个），每个约 3.6 万条文本

GXT 不按通用 0DRP 的子资源表处理；`DrpFile` 仍可用于 0DRP 头部/表结构，但内容语义交给 `GxtParser`。

## 8. 未解问题

1. `+0x08` / `+0x28` 两个指针的确切语义（是否指向特定表项/子结构）
2. `0xa8478889` 每条 16 B 记录的内部字段（已知与字符串一一对应，偏移/哈希编码未解）
3. `0x101` 每个 16 B 槽的字段语义（已知按 544 B 分块，共 K×34 槽）
4. `+0x20` 的小计数值与项数的关系（1/2/3，非严格相等）
5. `+0x48` / `+0x4C` 在 8.4% / 5.4% 样本上与项数不一致的原因
6. `seq 25904`（14.9 MB）特殊变体的布局
7. 表区尾部（`表项结束` 到 `+0x40`）是否存在其他结构
8. 13 种语言 × 1,107 份的配对关系（同一份内容的多语言版本如何对应）

## 9. 工具与 API

- `DrpFile::parse(const QByteArray&)` → 头部 + 表项 + 子资源切片
- `DrpFile::serialize()` → 结构化写回
- `DrpFile::roundTripOk()` → 字节级一致性
- `drpItems(const QByteArray&)` → 仅解析表项（轻量，供 UI 使用）
- `drpSectionName()` / `drpContainerKind()` / `drpTextPool()` / `drpPoolStrings()` /
  `drpTextLanguage()` → 段名、容器分类、字符串池与语言判定
- `languageKeyFromPath()` / `languageDisplayName()` → 从 `data/lang/<名称>_final.rpf`
  识别 13 种语言（american → 英文 …）
- `RpfReader::exportTextCorpus()` → 所有字符串池按语言导出为 `<语言>.tsv` + `_index.csv`
- CLI：`--drp <seq>` 输出段 ID + 段名；`--drp-verify` 全量校验；
  `--corpus <目录>` 导出 13 语言语料（371 万条）
- UI：属性栏「容器用途 / 段结构 / 字符串池 / 文本语言 + 写回校验」；
  文件属性「0DRP 分段」表 + 「文本池」页；主预览直接显示前 300 条字符串

## 10. 验证方法

1. 用 `--drp-verify` 遍历 `data.rpf` 内全部 `0drp` 类型资源
2. 对每个资源执行 `parse → serialize → 字节比较`
3. 统计 `total / valid / roundTripOk / fail`
4. 结果：15,755 / 15,754 / 15,754 / 1（见 §5）

该验证同时证明了：

- 表首/表尾指针解析正确
- 表项的 `size/hash/offset` 三元组解析正确
- 子资源切片边界正确
- 写回路径与解析路径对称
