# RPFExplorer —— RPF9 归档资源管理器

独立的 Qt 桌面程序。打开 GTA 系列的 `.rpf` 归档，**像解压缩软件一样浏览文件夹和文件**、预览与提取。

**设计原则：只做忠实读取，不臆造任何数据。**

打开后左侧是文件树：内嵌归档（如 `data/lang/american_final.rpf`）与
真实路径（如 `data/timecycle/timecycle_mods_1.xml`）都还原成文件夹结构；
双击文件即可导出，工具栏「导出全部」按目录结构批量提取。

```
dist/RPFExplorer.exe  <archive.rpf>                      # 图形界面（文件树）
dist/RPFExplorer.exe  --select <seq>  <archive.rpf>      # 打开界面并定位到指定资源
dist/RPFExplorer.exe  --extract <目录>  <archive.rpf>    # 提取全部 + 逐个 SHA-1 校验
dist/RPFExplorer.exe  --dump  -o out.txt  <archive.rpf>   # 结构信息
dist/RPFExplorer.exe  --csv   -o out.csv  <archive.rpf>   # 资源清单
dist/RPFExplorer.exe  --gxt <seq> -o out.tsv <archive.rpf># 按 GXT 文本表解析某个资源
dist/RPFExplorer.exe  --drp <seq> -o out.txt <archive.rpf># 0DRP 分段 + 写回校验
dist/RPFExplorer.exe  --embedded <seq> -o out.txt <archive.rpf> # 嵌入文件/资源名
dist/RPFExplorer.exe  --corpus <目录>  <archive.rpf>      # 导出 13 语言文本语料
```

> **命令行输出请用 `-o` 写文件。** 本程序是 GUI 子系统（无控制台），
> Windows 下标准句柄不可靠，`>` 重定向可能拿不到内容；
> `-o` 走的是 Qt 的文件写入，绝对可靠。
> 输出路径请用**绝对路径**——相对路径是相对**进程工作目录**，
> 不一定是你在 PowerShell 里 `Set-Location` 的位置。

## 三条铁律

### 1. 每个字段都标注来源

界面与 `--dump` 输出里，每个值都带来源列：

| 来源 | 含义 |
|---|---|
| **文件直读** | 直接从文件字节读出 |
| **计算得出** | 由文件字节扫描/计算得出（如 SHA-1、解压大小） |
| **外部佐证** | 来自游戏自身的清单 XML（如真实文件名） |
| **含义未明** | 原始字节可读，但语义尚未解明 |

未解明的字段一律显示「含义未明」，绝不猜测、绝不套用别处的解释。

### 2. 名字未知就写「未知」

RPF9 的目录表（条目表 + 名字表）整体加密，真实文件名**不可直接读取**。
但可以从归档**自身的内容**回收一部分真实名：

| 来源 | 方法 | 实测 |
|---|---|---|
| **清单 `<id>` 自引用** | 清单 XML 的 `<id>` 若形如路径，它就是该清单自己的真实名 | `common.rpf` 12 个 |
| **清单顺序映射** | 清单的 `<fileList>` 声明 N 个文件，紧跟其后的 N 个资源按序对应 | `common.rpf` 52 个 |
| **内嵌归档真名** | `core_language` 清单声明的 13 个 `data/lang/*.rpf`，再经 GXT 文字内容校验（中文包含汉字、日文包含假名……） | `data.rpf` 13 个归档 |

顺序映射**只在「扩展名与内容类型吻合率 ≥ 90%」时才采信**——宁缺毋滥。
实测 `TC_Files.meta` 的 50 个文件 98% 吻合（采信），而 `common.meta` 的
映射吻合率仅 28%（说明其文件在归档里被别的清单插开了，放弃）。

无真实名的文件按**内容魔数**命名（`文本表.gxt` / `PSIN资源.psin` / `图形.gfx` /
`数据.bin` …），不编造语义、不显示十六进制偏移。目录树形如解压缩软件：

```
common.rpf
├── data/
│   ├── anim/
│   │   ├── anim.meta            [清单 <id> 自引用]
│   │   └── cinematic.meta
│   ├── timecycle/
│   │   ├── TC_Files.meta
│   │   ├── timecycle_mods_1.xml [清单顺序映射]
│   │   └── …（共 50 个）
│   └── levels/americas/
│       ├── area.meta
│       └── props.meta
├── movies/Stinger/RSG_STINGER.bk2
├── 数据.bin      ← 无真实名，按内容类型命名
└── 清单.xml
```

导出时**有真实名用真实名**，没有就用 `序号_偏移_大小.bin`，不编造。

### 3. 覆盖率如实统计

状态栏与 `--dump` 都会显示：

```
数据区起点 / 数据区字节 / 资源个数 / 资源压缩字节（占数据区 %）/ 未计入字节
```

「未计入字节」= 数据区里**没有被任何已识别资源覆盖**的部分。
它们是空隙、未知结构或未识别的数据流，**不是**已解出的资源。
本工具不把它们伪装成资源，也不假装覆盖率是 100%。

## 读取的结构

```
0x000000  归档头 0x40 字节（魔数 "9FPR"）
0x000040  TOC 明文哨兵 32 字节（42 个归档逐字节相同）
0x000060  TOC 正文 = 条目表 + 名字/哈希区   ← 每归档加密，不可读
0x00004+0x04 处的值 = TOC 总大小（含 0x40 头）
（4KB 对齐(TOC 结束)）数据区 = 独立 zlib 压缩的 64KB 页，首尾相接
```

- **`+0x04` = TOC 总大小**：42 个归档（common + data 内 41 个内嵌）全部满足
  `(值 − 0x40) % 16 == 0` 且 `条目数×16 ≤ 值 − 0x40`；
  **数据区起点 = 4 KB 对齐上取整(0x40 + 值)**。
  26 个归档在起点处直接是 zlib 页（或隔 16 字节），1 个起点是内嵌归档头。
- **TOC 明文哨兵**：前 32 字节 `5f08daab…8969aad8` 在全部 42 个归档中逐字节相同。
- **TOC 正文加密**：13 个语言包的文件表结构相同，逐字节一致率仅 **0.39%**
  （随机水平 1/256 ≈ 0.39%），条目区 0.56%；除哨兵外没有任何相同的 16 字节块。
- **内嵌归档**：4 KB 对齐处的 `9FPR` 头，逐个列出（`data.rpf` 内有 41 个）
- **资源**：按 64KB 页合并规则切分

### 条目 vs 数据流

`+0x24` 是**条目数**（逻辑文件数），不一定等于解出的**数据流数**：

| 归档 | 条目数 | 解出数据流 | 说明 |
|---|---|---|---|
| 13 个语言包 | 1,115 | 1,115 | 1:1 |
| `0x00964000` | 156 | 0 | 数据区不是 zlib（未识别/疑似未压缩） |
| `0x009CA000` | 11 | 22 | 恰好 2 倍 |
| `0x1228E000` | 2,896 | 5,792 | 恰好 2 倍 |

2 倍的那些归档，解压内容成对出现：第一流以 `00…0050xxxxxx` 指针表开头，
第二流是数据体——与 RSC 的「系统页 + 图形页」形态一致。
无 TOC 时无法断言配对关系，本工具按**数据流**逐个列出，并同时显示条目数。

### GXT 文本表预览

`0DRP` 是通用资源容器（`data.rpf` 内 15,768 个），**只有 13 个语言包文本表是 GXT 结构**，
其余是普通二进制资源。选中资源时本工具按 GXT 结构做完整校验：

1. 槽位表筛选（`tag==1` 且标记 `==0`）条数 == 记录表条数
2. 记录表锚点 + 后 200 条 class/偏移单调校验
3. 串池基址按「偏移是否落在串首」投票实测
4. 记录地址逐条 UTF-8 解码，解码率 ≥ 50% 才认

校验通过才显示 GXT 面板：

- 表格列：序号 / 哈希 / 池 / 文本，3.6 万条也能秒开
- 筛选框：按文本内容或哈希前缀过滤
- 属性栏给出来源信息：条目数、非空数、记录表偏移、串池基址、解码率
- 工具栏「导出 GXT 文本…」导出 TSV（`idx / hash / class / text`）
- 非 GXT 的 0DRP 资源会明确标注「0DRP 二进制资源（非文本表）」，
  主视图直接列出**完整的可打印字符串**（严格 UTF-8 + NUL 结尾、≥8 字符）

### 导出文本（按类型自动解析）

左侧文件树支持多选（Ctrl / Shift）。工具栏「导出文本…」、文件菜单
「导出选中文本…」或资源右键「导出文本…」都会按类型自动选择解析方式：

| 类型 | 导出内容 |
|---|---|
| 0DRP 文本表（GXT 结构校验通过） | 每行 `哈希<TAB>文本` |
| XML / 纯文本 | 完整 UTF-8 原文 |
| 其它二进制（0DRP/psin/rbf/gfx/bin…） | 可打印字符串（`0x偏移  字符串`） |

导出方式二选一：

- **合并到一个文本文件**：每个资源前有分隔块（路径/真实名/偏移/大小/类型/解析方式）
- **分别导出为多个文件**：按树中的相对路径落盘，自动补 `.txt`；
  同名冲突追加 `~2`、`~3`；目录自动创建

进度条可取消。快捷键 `Ctrl+Shift+T`。

### 文件属性（右键，完整版）

右键资源 →「文件属性…」打开独立窗口，四个页签：

- 基本信息（路径、偏移、压缩/解压、页数、类型、SHA-1、字符串数）
- 字符串（完整，不截断）
- 文本（完整 UTF-8，不截断）
- 十六进制（完整；虚拟化表格按需渲染，大资源也不卡）

主界面不再显示截断的文本/十六进制预览——那两样统一放到这个窗口里看完整版。

|---|---|---|---|---|
| en | 36,888 | 0 | 0 | 2（TSV 把制表符写成空格，原文一致） |
| ja | 36,828 | 0 | 0 | 2（同上） |
| ru | 36,207 | 0 | 0 | 2（同上） |
| zh-Hans | 36,888 | 0 | 0 | 1（同上） |

### 资源内部结构（新增解析）

对最常见的两类资源，属性栏会给出按字节结构解析出的信息：

- **0DRP 容器头**：`+0x14` 恒为 `0x7A`、`+0x20` 多为 2、`+0x48/0x4C` 多为 4；
  `+0x08/+0x28/+0x38/+0x40` 是 `0x50xxxxxx` 运行期指针，减去 `0x50000000`
  就是资源内偏移（可校验是否越界）
- **GXT 判定不是「大就是文本表」**：>2MB 的 0DRP 还要通过完整结构校验
  （记录表锚点 + 有效槽位 + 文本解码率），否则按普通 `0drp` 资源命名。
  实测 data.rpf 里只有 **13 个** 真 GXT；另有 2 个 >2MB 的 0DRP
  （2.4MB、14.9MB）曾被误标为「文本表.gxt」，现在分别叫 `资源~N.0drp`。
- **导出的 `.gxt` 是游戏原始 0DRP 二进制**（不是文本文件）；要文本请用
  「导出 GXT 文本…」（TSV）或「导出文本…」（哈希+文本），或在表格里直接看。
- **PSIN 块表**：`{u32 标签, u32 大小, u64 0xAAAAAAAAAAAAAAAA}` × N。
  2,281 个 PSIN 里 2,225 个（97.5%）能按此结构解析出块数。
  **PSIN 是通用容器，不是音频格式**：实测内容包括多语种法律文本、哈希/索引表、
  嵌套 0DRP；2,281 个里 0 个含 OggS/RIFF/WAVE/XMA/Opus 等音频头，
  ffprobe 也无法识别。真正的音频样本应在未下载的 `audio.rpf`（28 GB）里。
- **RBF0 类名**：`u16 长度 + 类名 @0x0A`，1,260/1,263（99.8%）可读。
  实测分布：`rage__fwuiPrefab` 603、`fwuiAnimationNodeGraph` 190、`UIScreen` 136、
  `CMovieSubtitleContainer` 125、`UIMovieView` 65…… 说明这批 RBF0 主要是 UI 数据。
- **GFX 容器**：魔数 `GFX*` + 声明大小。严格校验（版本 1–60 + 声明长度合法）后，
  87 个 GFX 里**没有**真 SWF；直接搜 `FWS` 得到的 6 处是压缩数据里的偶然匹配。
- **嵌入的标准格式**（严格校验，全量统计）：只有 **1 个真 SWF**
  （seq 16916，3,014,656 B，`FWS` v3，声明长度与文件完全一致）。
  原始扫描出的 251 个 JPEG 候选**全部是压缩数据里的假标记**（SOI/EOI 偶然出现，
  段长度非法，ffprobe 无法解码）；BMP/RIFF/DDS 严格校验后为 0。
  此前的「BMP 530、JPEG 178、RIFF 16」是 ASCII 字符串等误报，已纠正。
- **XML / 纯文本**：主视图直接显示完整原文（不截断）

- **PSIN 结构化报告**（属性栏 / 文件属性「PSIN 结构」页 / 导出文本）：
  - 块链：`LSCH/LENM/LSNS/LGID/LRSC/CHKS` 及每块偏移、大小
  - 字段记录：LSCH 负载按 32 字节/条，输出 `hash(64位) + flags + off + aux`
    （字段名是哈希，不可逆；但结构、类型位、偏移可读）
  - 其它记录：未定型的 32 字节记录原样输出
  - 取值块：LSNS 头 `count/flags/size` + 文本片段
  - 找不到块链的文本/页索引变体：回退到 16 字节块表 + 全文文本片段
  实测例：seq 25712 是一份**车辆部件名列表**
  （`reversinglight_l`、`headlightcase_rf`、`kac_bonnet_dside_hinge`…）；
  按关键词归类 2,281 个 PSIN：车辆 37、法律/隐私 12、UI 2、动画 1，其余为表格/索引类。

### 0DRP 结构化解析与写回（DrpFile）

> 完整格式文档（头部字段表、表项布局、写回算法、未解问题、样例 hexdump）见
> **[docs/0DRP.md](docs/0DRP.md)**。

- 头部 0x60 字节；子资源表由 `+0x38`（表首）/`+0x40`（表尾）给出，
  每项 16B：`u64 (size<<32 | 段ID)` + `u64 (0x50000000 | offset)`
- **段 ID 不是名字哈希**：全量 60,585 个子资源只有 11 种段 ID，按组合分成 5 类容器
- **4 段文本包的字段关系已解明**：
  - `0x99331089` = 16 B 索引头 `{版本/标志, N, 3, 0}`
  - `0x10` = N 个 null 分隔字符串；`0xa8478889` = N × 16 B 记录表
    （14,418 / 14,418 个容器满足 `记录表字节数 = N × 16`）
  - `0x101` = K × 544 B 数据块（544 = 34 × 16 B 槽）
- **对白 / UI 文本包**（14,394 个，占 91.4%），其中 `0x10` 是 173.1 MB 的
  字符串池（418 万条），覆盖 **13 种语言 × 1,107 份**，
  含任务对白（`~sl:` 时间轴）、UI 文本与游戏内媒体新闻稿
- `DrpFile::parse()` → 结构；`serialize()` 按结构重写头部指针、表项与子资源切片，
  未建模区域原样保留；`roundTripOk()` 做字节级比对
- 全量 `data.rpf`：**15,755 个 0DRP，15,754 个解析成功且写回字节一致**
  （唯一失败：seq 25904，14.9 MB 的特殊变体）
- CLI：`--drp <seq>` 单文件分段+写回；`--drp-verify` 全量校验
- UI：属性栏显示「容器用途 / 段结构 / 字符串池 / 文本语言」；
  主预览直接显示前 300 条字符串；文件属性里有「0DRP 分段」和「文本池」页
- 性能：`data.rpf` 扫描从约 40s 降到 **11.2s**（复用首屏解压结果、去除重复解压），
  25,909 条资源与优化前逐行一致（0 差异）

### 多语言语料导出

「文件 → 导出多语言语料…」或 CLI `--corpus <目录>`：

- 从路径 `data/lang/<名称>_final.rpf` 识别 13 种语言（american → 英文 …）
- 每种语言一个 TSV：`seq \t 序号 \t 文本`，另有 `_index.csv` 记录容器/条数/路径
- data.rpf 实测：**14,469 个容器、3,711,568 条字符串、约 141 MB**
- 13 种语言各约 28 万条，首条对白是同一条的 13 种翻译
  （“Hey! Eyes open!” / “喂！盯好了！” / “目を離さないで！” …）

### 未知二进制里的真实资源名

- 6,510 个 `bin` 中，**2,925 个嵌有真实资源名**，树里直接用该名字显示
- 例：`w_ar_adb_01.#dr`（武器）、`ptfx_model_mussels_01.#dr`（粒子）、
  `amb_lights.#dr`（环境光）
- 共识别 **3,175 个唯一名字**（`w_` 2,828、`ptfx_` 262 等）
- 名字只来自文件内字符串表，不做拼接/猜测；没有名字的仍显示 `数据~N.bin`
- 属性栏「内嵌资源名」，预览顶部列出全部；CLI `--embedded <seq>` 同样输出

### 未压缩数据块统计

数据区里未被 zlib 流覆盖、≥4 KB 且含非零字节的区间，单独统计为
「疑似未压缩数据块」（`--dump`、内嵌归档属性里都有）：

| 归档 | 段数 | 字节 | 其中非零 |
|---|---|---|---|
| `common.rpf` | 43 | 544,200 | 211,718 |
| `data.rpf` | 266 | 19,954,758 | 18,788,738 |
| `0x00964000` 内嵌归档 | 1 | 409,600 | 约 70% |

实测 `0x00964000` 归档的数据区（400 KB）不是 zlib / gzip / bz2 / lzma / zstd /
LZ4 / Snappy，熵 6.37、4 KB 周期有 12% 字节相同、含 `0x50xxxxxx` 指针——
**判定为未压缩的结构化数据**，不是加密。边界仍在加密 TOC 里，所以只统计、不臆造文件名。

### 64KB 页合并规则

一个资源由若干连续 64KB 页组成：

- 某页解压长度恰为 65,536 的整数倍时，下一页仍属同一资源
- 否则该页是末页
- 合并还要求物理连续：页间间距 0–16 字节，且填充全为 `0x00`

### 已知的缺口（如实呈现）

- **`common.rpf`**：资源压缩字节占数据区 **85.6%**，未计入 948,993 字节
  = 全零填充 729,951 + 非零未识别 219,042（274 段）
- **`data.rpf`**：占 **87.9%**，未计入 58,171,802 字节

## 已知限制

1. **真实文件名部分可得**。RPF9 目录表加密，无法直接读取文件名；
   但可从归档自身的清单 XML 回收一部分（见上「名字未知就写未知」）。
   `common.rpf` 实测 63/277 = 22.7%，其余无任何佐证，一律显示「未知」。

   加密本身的取证（2026-11-21）：

   - 42 个归档的 TOC 前 32 字节**明文哨兵完全相同**，其后正文全部不同；
   - 13 个语言包文件表结构相同，逐字节一致率仅 0.39%（= 随机水平），
     且条目区、名字区在 4 字节粒度上也没有任何稳定字段；
   - 已逐一实测并排除：AES-128/256 的 ECB / CBC / CTR / CFB / OFB
     （密钥候选含 32 字节哨兵、其 SHA-256、头部 0x10 的 u64、全零），
     ChaCha20、RC4、周期 XOR，GTA5 Xbox / PS3 的 32 字节 RPF 密钥，
     明文哈希（joaat/crc32/md5/sha1）、明文偏移/大小全盘搜索；
   - 结论：正文是**每归档独立密钥**的加密，密钥应在游戏可执行文件内；
     本次下载只有 `common.rpf` + `data.rpf`，无 exe，因此**无法继续解密**。
2. **部分数据区未识别**。见上「已知的缺口」；界面/dump 已把「未计入」
   拆成全零填充与非零未识别两部分，不混为一谈。
3. **`+0x08 / +0x0C / +0x10 / +0x20 / +0x28` 语义未解明**，
   界面上标为「含义未明」。已解明的是：
   `+0x04` = TOC 总大小、`+0x24` = 条目数、`+0x28` 只有 5 种取值（类别标记）。
